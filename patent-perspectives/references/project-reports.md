# 项目评审与中长期储备报告

给具体项目编写报告时，先写一条读者看完本节就能作出的判断，紧接着写适用边界。读者可从结论直接回到研究原文或项目材料。确认过的[离线网页版](report-templates/打开网页.html)可搜索示例并下载空白稿。编写前按本次读者读取下表中的完整原稿和[共用证据底稿](report-templates/00-使用说明与证据底稿.md)；其中的金额、工期、研发试验、虚构主体、图和教学权项仅供理解写法。正式报告使用本次取得的材料。

| 读者与已确认模板 | 近期预研的九项问题 | 中长期储备的主要判断 |
|---|---|---|
| [企业决策者](report-templates/01-企业决策者-专利报告模板.md) | 本次授权、业务边界、机会与威胁、能力缺口、进入障碍、经营方案、投入与经济性、阶段门槛、决策记录 | 为什么保留这个未来选项，消耗什么资源，哪种信号会改变投入 |
| [研发总监](report-templates/02-研发总监-专利报告模板.md) | 研发决定、范围与证据、结构拆解、技术演进、同工况比较、专利约束、能力资源、验证条件、阶段计划 | 哪个机理或能力值得先研究，依赖什么，最小研究能排除哪种解释 |
| [专利总监](report-templates/03-专利总监-专利报告模板.md) | 本次专利决定、检索范围、权利辖区、权项对照、自有组合、申请保密、处置选择、预算期限、复核监测 | 针对何种未来用途保留哪类权利选择，哪些范围、成本和条件仍待核 |

**选用范围。** 已明确要求完整三份模板时，覆盖各角色获委托的全套模块。仅问一个选择时，选能回答该问题的角色和模块；所需材料未取得，就在该节写明对判断的影响与补证安排。近期与储备按用途区分，可以同时存在，可共用材料编号。储备可以有当期预算，复核可以按日期、周期或事件安排。纯技术理解、公司画像、行业研究和外观决定书研究沿用原有研究流程，成果可以是解释、差异或未决问题。

## 用同一底稿写出三种不同的回答

- **经营。** 把代表文献与主体、公开时间、解决的问题和影响本方的选择串起来。只能证明某主体有公开申请时，可以写“跟踪它后续怎样处理这一失效；下一轮样机评审前核对最新公开件”。写“追加投资”还需要项目预算、需求等相应依据。建议额度、已获批准额度和后续量产投入分开。
- **研发。** 在底稿表 A 分别登记 A、B 两份图的版本和具体位置，再在表 B 引用两处编号，写出观察到的差异、能支持的结论、不能支持的效果，以及表 D 对应的验证任务。图示受力方向、真实装配位移、测得密封性能分别记录。试验写实际工况、可比条件、通过条件与尚缺材料；教学数值不作为通用指标。
- **知产。** 交代法域、产品版本、所读文本及法律状态观察日。保留逐项限定的动作主体、动作、对象和结果，让每条限定对应各方案的已知事实与待取证事项。例如，若限定为“锁紧件使滤芯沿轴向移动”，锁紧后的压力不能证明位移由锁紧件造成。此时可比较用户插入结束、锁紧件开始动作、锁紧完成三个时点的位置和施力者；其他机构按自己的动作过程选择时点。缺授权文本、产品证据或状态时分别说明。正式侵权、有效性和自由实施判断另行专业复核。
- **储备。** 写保留理由、目前是哪一级证据、什么会推翻设想、尚缺什么、最小任务、负责人及资源、何时复核，以及转入近期或关闭的条件。没有真实需求或预算时，明确写“待确认”，并说明谁需提供什么。

## 将填写结果接入报告

阅读版把 `reader_contract` 放在阅读 JSON；全景版放在 `--report-context`。两者沿用第 2 版契约和既有研究门禁，在 `reader_contract.project_report` 写入本项目的章节。旧数据和纯研究省略整个字段。原有 `role_guides` 仍说明每个角色的阅读重点。

- `context` 是读者首屏需要的产品、项目、阶段或用途，用简短一句。主读者须有对应项目章节。每节有 `role`（management、rd、ip）、`horizon`（near、reserve）、`question_id`、`decision` 和 `standing`（proposed 建议、pending 待判断、approved 已有授权）。近期再填 `module` 1–9，储备不填模块号。章节顺序按用户任务安排。
- `question_id` 指向 `reader_contract.questions`，同一问题在不同角色共用同一答案、边界和原文编号。正式项目把标记 answered 的答案和证据集合与已通过的研究复核逐项对齐；本节新增的项目佐证另列 source_ids，项目建议独立写在 `decision`。当前无法判定时，用 insufficient，说明影响和补证。已有授权还须在 `approval_ref` 给出类型为 authorization 的项目原件，记录批准范围。
- 每节写 `gap`、`next_step`、`resources`。近期的 `gate` 写继续、调整、暂停的判据。储备另填 `reason`、`maturity`、`review`、`promote`、`close`。未知项写实际缺口及影响，不自行填入日期、费用或人员。
- 编号为研究库原文 ID 时直接沿用，项目内部资料另列在 `materials`。每份材料填 `id,title,origin,version,locator,observed_on,excerpt,limit`，分别是编号、标题、发布或持有人、版本、页图或时点位置、核查日期、原文或图示记录、所能证明的边界。编号须唯一。研究问题的 `evidence_ids` 仍引用原研究证据；章节等处的 `source_ids` 可同时引用实际研究证据和登记的项目材料。内部来源打开材料摘录，研究来源打开已绑定的原文。
- 有竞争动向时，`signals[]` 每项写 `organization,document,time,finding,implication,source_ids`。有可比较路线时，`routes[]` 各写 `label,observation,source_ids`；每项绑定自己的定位，未取得另一方案资料时在缺口写明。有图时 `figures[]` 按比较顺序引用材料编号，材料的 `figure` 含 PNG 字节的 Base64、SHA-256 和图注，字段为 `png_base64,sha256,caption`。需要窄屏突出细节时，另给 figure.detail=[x,y,width,height]，使用原图像素指定确切区域，完整原图仍可打开。未指定时完整显示，避免自动裁掉证据。图注用正常字号解释观察位置、标记含义和适用条件；渲染核对字节，编写人还需人工核对来源与图注。
- 需逐项对照权利要求时，先写该节的 `right`（territory、version、status）。未核验状态写 unknown；已观察写 observed，并给 as_of、finding 和登记来源 source_ids。外部提供的权项原件在 materials 中标 kind=claim。`claims[]` 每项给 `source_id,wording,need,cases`。wording 是所引权项的连续原文；need 写还要取什么证或由谁复核。cases 按方案写 `label,observation,status,source_ids`，status 为 observed 或 pending。观察事实必须有出处；尚未取得的保留 pending。需要区分装配或操作阶段时，另写 `observations[]` 的 `stage,check`。产品来源、权项文本与法律状态应有独立定位。

下例是一个储备章节的**字段演示**。使用时替换为本项目已有的研究问题编号及实际材料。

```json
  "standing": "pending", "decision": "先保留解锁前止水的研究选项。",

  "close": "需求被排除后，先核查其他产品或合同依赖，再评估关闭。"
}
```

## 交付前怎样复看

分别打开管理、研发和知产首节，再直达其中一项储备。窄屏上的“当前模块”应与正文一致；首屏能够读完整的本节判断及关键边界。切换角色后，原文和证据成熟程度保持一致。点一条专利原文和一份项目资料，核对版本、位置与实际支持的句子。对照表在手机上按具体限定、各方案、取证要求连续阅读；研发图可放大并回到原位。试一次跨角色的项目章节搜索。纯研究样例单独检查。模型复核、浏览器模拟和真实负责人试读分别记录。
